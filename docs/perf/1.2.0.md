# Re-measure after the 1.2.0 load fixes

Same machine as [1.1.1.md](1.1.1.md). Linux 6.12.113+ x86_64, Intel(R) Xeon(R) Processor, MemTotal 16387328 kB, rustc 1.83.0 (90b35a623 2024-11-26).

The 1.1.1 column is this machine, release build, before the 1.2.0 edits. It is not the stress-test host. The shape is the same kind of store: claim `i` points at `plan-1/step-(i mod steps)` and `test:t(i mod results)`, and each row carries a short `command` or `recorded_at` that a selector does not need. Wall time is one run. RSS is `VmHWM`.

The 100,000-step Trammel file was 14.9 MiB and the 200,000-result Chisel file was 11.5 MiB. A page of that pair is about 63 MiB RSS with 1,000 claims and about 72 MiB with 20,000 claims. That is about 2.4 times the two files, not one times. 1.1.1 held the parsed tree and was 227 to 238 MiB on the same files.

The 63 MiB file is one step plus a long `command` string the selector does not keep. 1.2.0 peaks at 129 MiB (about twice the file). 1.1.1 peaked at 191 MiB. The file is still read whole. The 64 MiB cap is unchanged.

A page and a full view of the same evidence are close. Both build one index. On the 20,000-claim, 100,000/200,000 store, `--limit 1` was 0.35 s on the 1,000-claim copy and `--limit 500` was 0.48 s; the full 20,000-claim view was 0.50 s. Judging the extra claims added about 20 ms. What went away is the product of claims and rows: 1.1.1 spent 249 s on the first page of 500 and another 257 s on the next page. 1.2.0 does not get cheaper than reading the snapshots, and `--limit 1` does not skip that read.

`check` on 1,000 claims and the large pair dropped from 199 s to 0.34 s. It uses the same index as `view` and does not spawn git. The 32-claim check of the 63 MiB file dropped from 6.1 s to 0.16 s.
