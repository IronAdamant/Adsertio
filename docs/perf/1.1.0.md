# Performance after the 1.1.0 read changes

Same harness and machine as [baseline-1.0.0.md](baseline-1.0.0.md). Measured with the cache and the Probatio fast path in this commit.

```sh
cargo test --release --locked --test perf -- --ignored --nocapture
```

## What changed

- One `view` call parses a Trammel snapshot, a Chisel snapshot, or a Probatio `results/` directory once, and reuses it for every claim that points at that path. The cache is dropped when the call returns. A read outside `view` does not use it, so a later read sees a file that was rewritten.
- A regular file under a Probatio `results/` directory that is already inside the project is read in place. A symlink still goes through the full path check, so a link out of the project stays `unreadable`.

## Before and after

Median, then p95. Before is the baseline note. After is this commit, same VM.

| Path | Before | After |
|---|---|---|
| 100 claims, one 1,000-step Trammel store | 44.2 / 47.4 ms | 4.1 / 4.3 ms |
| Probatio `results/`, 1,000 files | 7.0 / 10.3 ms | 4.5 / 5.5 ms |
| Probatio `results/`, 10,000 files | 75.2 / 130.0 ms | 50.8 / 54.2 ms |
| CLI `--version` | 727 / 1087 us | 695 / 1076 us |
| MCP warm `ls` on an empty store | 16 / 75 us | 25 / 99 us |
| `ls`, 10,000 claims | 41.6 / 74.3 ms | 41.5 / 55.2 ms |
| `view`, 10,000 claims, no evidence | 39.0 / 49.4 ms | 45.9 / 54.8 ms |
| `view --id`, 10,000 claims | 28.0 / 37.1 ms | 39.6 / 57.9 ms |
| Trammel store, 10,000 steps, one claim | 7.6 / 10.0 ms | 7.4 / 12.0 ms |
| Chisel store, 10,000 results, one claim | 5.6 / 5.7 ms | 5.8 / 5.8 ms |
| Ledger, 10,000 entries | 8.4 / 11.4 ms | 6.7 / 7.7 ms |

## What did not improve

Listing and viewing claim files is still one read and one parse per file. `view --id` still reads every sibling, because a damaged claim fails the whole view. Those rows moved by a few milliseconds with five to eleven samples, which is noise on this VM, not a speedup.

A single large JSON snapshot (one Trammel or Chisel store, one claim) was already a parse of one file. Caching it does nothing when nothing else points at it. Cold start and a warm MCP call on an empty store were already under a millisecond and did not get faster.

The ledger at 10 entries had a wild p95 in the baseline (9 ms against a 0.8 ms median). The later run did not show that spike. It is not counted as a win.
